# راهنمای بستهٔ سروری نوا برای IT

این بسته همان رابط وب نوا را روی لینوکس و دامنهٔ داخلی شرکت ارائه می‌کند؛ ظاهر چت، تنظیمات و امکانات وب تغییر نمی‌کند. پیش‌فرض‌ها برای **Active Directory لوکال، سرویس ورود داخلی و گواهی سازمانی** تنظیم شده‌اند. ورود به حساب Microsoft آنلاین نیاز نیست. نصب برنامه روی کامپیوتر کاربران لازم نیست.

**راهنمای اصلی این محیط: [چک‌لیست کامل AD لوکال و گواهی‌های شرکت](onprem/README.fa.md).**

**صفحهٔ ورود هماهنگ با نوا:** تم آمادهٔ Keycloak، انگلیسی و مینیمال با حالت روشن/تاریک خودکار سیستم، داخل بسته است. [نصب تم، برند شرکت و پیش‌نمایش محلی](keycloak/README.fa.md). نصب تم روی سرویس Keycloak توسط IT انجام می‌شود؛ فرم‌های احراز هویت همچنان اصلی هستند.

## اتصال به Active Directory

روش پیشنهادی **OIDC / ورود یکپارچه** است، نه ارسال مستقیم نام کاربری و رمز AD به نوا:

- اگر AD FS داخلی نسخهٔ ۲۰۱۶ به بعد دارد: از OIDC همان سرویس استفاده شود.
- اگر فقط AD داخلی دارد: IT می‌تواند Keycloak را به AD از طریق LDAPS متصل کند و نوا به OIDC آن وصل شود. نصب و پیکربندی دایرکتوری/Keycloak جزو این بسته نیست.

API مدل هوش مصنوعی با ورود سازمانی فرق دارد. رمز کارمند فقط در صفحهٔ سامانهٔ هویت شرکت وارد می‌شود؛ نوا آن را دریافت یا ذخیره نمی‌کند.

## نصب روی سرور

پیش‌نیاز: لینوکس، Docker Engine و Compose v2، DNS داخلی، دسترسی HTTPS کاربران به نوا و سرویس ورود، و ارتباط خصوصی Keycloak به AD. دانلود وابستگی‌ها و آپدیت‌ها نیاز به دسترسی خروجی یا mirror داخلی IT دارند؛ محلی‌بودن AD به معنی نصب کاملاً بدون اینترنت نیست. برای شروع با کاربران محدود، ۲ هسته و ۲ گیگابایت RAM صرفاً نقطهٔ شروع نواست؛ منابع Keycloak/دیتابیس آن جداست. این سرور مدل را اجرا نمی‌کند و به Provider متصل می‌شود.

فایل `IDK-Nova-Server-X.Y.Z.tar.gz` و فایل `.sha256` کنارش را از یک Release رسمی بگیرید. دستورهای واقعی نصب در [راهنمای کامل انگلیسی](README.md) هستند. پس از بررسی checksum و استخراج، اجرا کنید:

```sh
sudo bash install.sh /opt/idk-nova
```

سپس فقط این دو فایل را تنظیم کنید:

1. `/opt/idk-nova/config/config.json`: دامنهٔ `publicOrigin`، آدرس issuer هویت، client ID، گروه‌های مجاز، Providerها، مدل‌ها، تم و نام/لوگوی شرکت.
2. `/opt/idk-nova/config/.env`: `NOVA_DOMAIN`، کلید محرمانهٔ OIDC و API Key مشترک شرکت. این فایل نباید منتشر یا برای کاربر فرستاده شود.

در سامانهٔ هویت، آدرس بازگشت را دقیق ثبت کنید:

```text
https://nova.company.internal/auth/callback
```

دامنهٔ نمونه را با دامنهٔ واقعی عوض کنید. آدرس باید ریشهٔ دامنه باشد، نه مسیر زیرپوشه. برای Providerهایی با یک کلید و چندین مدل، فقط یک ورودی Provider و یک متغیر API Key کافی است؛ مدل‌ها در لیست همان ورودی قرار می‌گیرند.

نمونهٔ `allowedGroups` روی `nova-users` محدود شده است. گروه واقعی AD باید به claim آرایه‌ای `groups` در ID token نگاشت شود و مقدار آن دقیقاً با کانفیگ نوا یکی باشد. اگر mapper مقدار `/nova-users` می‌دهد، همان را بنویسید. نبودن claim باعث رد دسترسی می‌شود. لیست خالی یعنی همهٔ حساب‌های موردقبول سرویس ورود، نه ورود ناشناس؛ بدون تصمیم امنیتی آن را خالی نکنید.

بعد اجرا کنید:

```sh
sudo /opt/idk-nova/manage.sh start
sudo /opt/idk-nova/manage.sh status
```

نصب جدید، override داخلی را آماده می‌کند. قبل از شروع، CA شرکت را در `config/ca/company-ca.pem`، گواهی HTTPS نوا را در `config/tls/server.crt` و کلید خصوصی متناظر را در `config/tls/server.key` قرار دهید. Caddy از همین گواهی استفاده می‌کند؛ صدور گواهی عمومی یا بازکردن AD به اینترنت لازم نیست. دستگاه کاربران نیز باید CA را بشناسند. خطای گواهی را با خاموش‌کردن بررسی امنیتی دور نزنید.

## آپدیت و بازگشت

```sh
sudo /opt/idk-nova/manage.sh check
sudo /opt/idk-nova/manage.sh update vX.Y.Z
sudo /opt/idk-nova/manage.sh rollback
```

نسخهٔ واقعی منتشرشده را به‌جای `vX.Y.Z` بگذارید. ابزار جدید کانال مستقل `server-vX.Y.Z` را می‌خواند. آپدیت با تأیید مدیر سرور انجام می‌شود؛ checksum بررسی می‌شود و کانفیگ، کلیدها و گواهی‌ها جدا باقی می‌مانند. اگر نسخهٔ جدید سالم بالا نیاید، استقرار قبلی برگردانده می‌شود. برای مهاجرت از 0.31.0، نصب دستی نسخهٔ جدید و فرمان `use` در راهنمای AD لوکال توضیح داده شده؛ کانفیگ قدیمی خودکار عوض نمی‌شود. کاربران با Refresh کد جدید را می‌گیرند و ممکن است ورود دوباره لازم شود.

## مرز قابلیت‌ها و داده‌ها

- کلید مشترک شرکت در مرورگر کارمند ارسال نمی‌شود. درخواست‌های مدل از مسیر سرور عبور می‌کنند.
- چت‌ها و فایل‌های آپلودی در حافظهٔ مرورگر کاربر می‌مانند و برای هر هویت OIDC جدا می‌شوند؛ **همگام‌سازی تاریخچه بین دستگاه‌ها در این بسته وجود ندارد**.
- ورود سازمانی به معنی پشتیبان‌گیری از چت‌ها، رمزنگاری حافظهٔ مرورگر یا محدودیت قطعی خروج داده به همهٔ Providerها نیست. روی دستگاه مشترک از پروفایل مرورگر جدا استفاده کنید.
- کنترل سیستم، اجرای فرمان، GGUF و Work بومی که در وب غیرفعال‌اند، با این بسته فعال نمی‌شوند. سرور جای کامپیوتر شخصی کاربر را نمی‌گیرد.
- با این تنظیمات، یک نمونهٔ سرور اجرا کنید. چند نمونه پشت Load Balancer بدون session store مشترک پشتیبانی نمی‌شود.
- توقف حساب AD بلافاصله session فعلی نوا را لغو نمی‌کند؛ در ورود دوباره یا پایان اعتبار نشست اعمال می‌شود. MFA و سیاست حساب را در IdP مدیریت کنید.
- خروج محلی از مسیر `/auth/logout` است و به معنی خروج از کل سامانهٔ هویت شرکت نیست.

قبل از ارائه به کاربران، IT باید با AD واقعی شرکت، حساب مجاز و غیرمجاز، مدل واقعی، پاسخ استریم، دو حساب متفاوت، دامنه/گواهی و یک آپدیت/rollback آزمایش کند. تست‌های پروژه با سامانهٔ هویت آزمایشی امضاشده انجام می‌شوند؛ ادعای تست روی AD شرکت شما نداریم.
