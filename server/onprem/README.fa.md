# استقرار نوا با Active Directory لوکال شرکت

AD شرکت داخلی است؛ این بسته برای احراز هویت به Entra ID، حساب Microsoft آنلاین یا سرویس ابری نیاز ندارد. لوکال‌بودن AD با «کل سرور بدون اینترنت» یکسان نیست: دریافت Docker imageها، وابستگی‌های نصب و آپدیت GitHub به دسترسی خروجی نیاز دارد. اتصال به مدل هم مستقل است؛ می‌تواند Provider داخلی یا خارجی باشد.

## معماری ورود

اگر شرکت AD FS سازگار با OIDC دارد، از issuer واقعی آن استفاده کنید. اگر فقط Domain Controller دارد، یک Keycloak داخل شبکه راه‌اندازی کنید و LDAP Federation آن را به AD از طریق LDAPS متصل کنید. نوا فقط OIDC سرویس داخلی را می‌بیند؛ نام کاربری/رمز AD یا Bind Password در کانفیگ نوا قرار نمی‌گیرد.

**Keycloak و دیتابیس پایدار آن خودکار توسط این بسته نصب نمی‌شوند.** این‌ها باید توسط IT آماده، پشتیبان‌گیری و نگه‌داری شوند. از `start-dev` برای محیط عملیاتی استفاده نکنید. سرور لینوکسی نوا برای این مسیر نیازی به Join شدن به دامین ندارد. ورود خودکار ویندوز/Kerberos قابلیت جداگانه است، نه نتیجهٔ خودکار اتصال LDAP.

## اطلاعاتی که IT باید آماده کند

| مورد | نمونه / توضیح |
| --- | --- |
| دامنهٔ AD | دامنهٔ واقعی داخلی شرکت؛ مقادیر نمونه را جایگزین کنید |
| Domain Controller | `dc01.company.internal`؛ ترجیحاً FQDN منطبق با گواهی |
| اتصال AD | `ldaps://dc01.company.internal:636` |
| Users DN / Base DN | `OU=Employees,DC=company,DC=internal` |
| Bind identity | حساب سرویس کم‌دسترسی برای خواندن/جست‌وجوی کاربران و گروه‌ها |
| نام ورود | `sAMAccountName` یا `userPrincipalName` طبق سیاست شرکت |
| گروه مجاز | مثلاً `nova-users`؛ عضویت و claim باید واقعاً نگاشت شود |
| CA سازمان | ریشه/واسط مورداعتماد برای TLS داخلی؛ بدون Private Key مربوط به CA |
| دامنهٔ نوا | `nova.company.internal` در DNS داخلی |
| دامنهٔ ورود | `sso.company.internal` در DNS داخلی |

دسترسی Bind باید خواندن اطلاعات موردنیاز در OUهای مربوط باشد؛ Domain Admin، ساخت کاربر، تغییر رمز یا نوشتن روی AD لازم نیست. LDAP در Keycloak را در حالت **READ_ONLY** بگذارید. رمز حساب سرویس فقط به‌صورت امن در سامانهٔ هویت تنظیم شود؛ آن را در ایمیل/تیکت عمومی نفرستید.

## تنظیم Keycloak

1. یک realm مثل `company` ایجاد کنید؛ از realm مدیریتی `master` برای کاربران نوا استفاده نکنید.
2. در User Federation، LDAP با Vendor مناسب Active Directory، LDAPS، حساب Bind و Users DN واقعی تنظیم کنید. CA گواهی DC را در truststore سرویس Keycloak اضافه کنید؛ بررسی گواهی/hostname را خاموش نکنید.
3. اتصال و ورود یک حساب واقعی آزمایشی را بررسی کنید. مپینگ username، نام و ایمیل را مطابق AD تنظیم کنید؛ وجود ایمیل شرط ورود در کد نوا نیست.
4. یک OIDC client محرمانه با ID نمونهٔ `nova-web` بسازید: Client Authentication روشن، Standard/Authorization Code Flow روشن، PKCE با S256، بدون Implicit Flow و بدون Direct Access Grants برای نوا.
5. Redirect URI را دقیقاً `https://nova.company.internal/auth/callback` ثبت کنید؛ wildcard نگذارید. دامنه را با دامنهٔ واقعی عوض کنید.
6. گروه‌های AD را به Keycloak و سپس یک claim آرایه‌ای به نام `groups` در **ID token** نگاشت کنید. مقدار ارسالی دقیقاً باید با `allowedGroups` یکی باشد. اگر mapper مقدار `/nova-users` می‌دهد، همان `/nova-users` را در نوا بنویسید، نه `nova-users`.
7. issuer واقعی را از OIDC discovery بگیرید؛ نمونه: `https://sso.company.internal/realms/company`. تمام endpointهای discovery باید از سرور نوا قابل دسترسی و مورداعتماد باشند.

## ظاهر صفحهٔ ورود

پوشهٔ `keycloak/themes/nova` داخل این بسته، تم مخصوص سرویس ورود داخلی است. آن را روی Keycloak موجود mount کنید و Login theme را در realm شرکت روی `nova` بگذارید. ورود انگلیسی و ساده، تم خودکار سیستم، لوگو/رنگ شرکت و پیش‌نمایش بدون AD در [راهنمای تم](../keycloak/README.fa.md) است. تم به‌تنهایی realm یا سیاست ورود را تغییر نمی‌دهد و برای AD FS قابل نصب نیست؛ برندینگ AD FS مسیر جداگانه دارد.

## فایل‌های نوا

در نصب جدید، `install.sh` تنظیم داخلی را در `config/compose.override.yaml` قرار می‌دهد. دو کانفیگ اصلی:

- `config/config.json`: آدرس واقعی نوا، issuer داخلی، client ID، گروه‌های مجاز و مدل‌ها.
- `config/.env`: دامنهٔ نوا، Client Secret صادرشده توسط سرویس ورود داخلی و API Key مدل. مقادیر شامل `$` و `#` را مطابق قواعد Compose داخل single quote بگذارید.

نمونهٔ `issuer` هیچ وابستگی به Microsoft Online ندارد. نمونهٔ Provider مدل هم داخلی است و باید با endpoint و model ID واقعی شرکت جایگزین شود. اگر Provider کلید لازم ندارد، فیلد `apiKeyEnv` همان Provider را حذف کنید؛ خاموش‌کردن احراز هویت نوا راه‌حل نیست.

گواهی‌های واقعی را در این مسیرها بگذارید:

```text
/opt/idk-nova/config/ca/company-ca.pem
/opt/idk-nova/config/tls/server.crt
/opt/idk-nova/config/tls/server.key
```

- `company-ca.pem`: مجموعهٔ PEM گواهی‌های CA ریشه/واسط مورداعتماد برای SSO و APIهای داخلی. نوا از `NODE_EXTRA_CA_CERTS` استفاده می‌کند و اعتمادهای استاندارد Node را نیز نگه می‌دارد.
- `server.crt`: گواهی HTTPS نوا همراه زنجیرهٔ واسط لازم، دارای SAN برابر نام واقعی دامنهٔ نوا.
- `server.key`: کلید خصوصی متناظر گواهی نوا، بدون رمز تعاملی برای راه‌اندازی خودکار؛ آن را فقط در اختیار مدیر سرور بگذارید (`chmod 600`).

CA ریشه/واسط را روی دستگاه کاربران هم مورداعتماد کنید؛ مثلاً با سیاست سازمانی. فایل Private Key مربوط به CA هرگز لازم نیست. گواهی نوا را با گواهی DC یا سرویس SSO اشتباه نگیرید؛ نام‌ها و کاربردشان متفاوت است.

در این حالت Caddy از گواهی شرکت استفاده می‌کند و برای صدور گواهی به Let's Encrypt، DNS عمومی یا بازکردن AD روی اینترنت نیاز ندارد. پورت ۸۰ در تنظیم پایه فقط می‌تواند برای هدایت به HTTPS استفاده شود؛ سرویس اصلی روی ۴۴۳ است.

## شبکهٔ داخلی

| مبدأ | مقصد | دسترسی |
| --- | --- | --- |
| مرورگر کاربران | نوا و Keycloak/AD FS | HTTPS 443 و DNS داخلی |
| نوا | Keycloak/AD FS و endpointهای discovery آن | HTTPS 443 |
| Keycloak | Domain Controller | LDAPS 636 |
| نوا | Provider مدل | فقط پورت endpoint واقعی شرکت |

DNS و ساعت سرورها درست باشند. اگر سرویس‌ها خارج شبکه قرار دارند، مسیر خصوصی/VPN لازم است؛ DC را روی اینترنت منتشر نکنید. مرورگر کاربران هم باید بتواند نام و گواهی سرویس ورود را بشناسد؛ فقط دسترسی کانتینر کافی نیست. برای DNS خاص Docker، تنظیم `dns` را در override پایدار شرکت اضافه کنید. استفاده از FQDN واقعی و Split DNS بهتر از جایگزین‌کردن issuer با IP ناسازگار با گواهی است.

## شروع و آزمایش

```sh
sudo /opt/idk-nova/manage.sh start
sudo /opt/idk-nova/manage.sh status
```

قبل از استفادهٔ کارمندان: ورود کاربر مجاز و غیرمجاز، گروه‌ها، گواهی‌ها، خروج/انقضای نشست، پاسخ واقعی مدل و دو حساب متفاوت را تست کنید. عدم وجود `groups` مجاز، خطای ۴۰۳ می‌دهد؛ مشکل mapper را اصلاح کنید، نه اینکه بدون تصمیم امنیتی گروه‌ها را حذف کنید. تغییر CA یا کانفیگ نیازمند راه‌اندازی دوباره است. پس از راه‌اندازی مجدد ورود دوبارهٔ کاربران طبیعی است.

## مهاجرت از بستهٔ 0.31.0

آپدیت، دامنه/issuer/کلیدهای قبلی را خودکار عوض نمی‌کند. ابتدا کانفیگ‌ها را پشتیبان بگیرید. با ابزار قبلی می‌توانید نصب‌کنندهٔ نسخهٔ جدید را از کانال کامل موجود بگیرید؛ برای این patch مستقل، آرشیو Server جدید را دانلود و checksum را بررسی کنید، استخراج کنید و `install.sh` همان نسخه را با مسیر نصب قبلی اجرا کنید. سپس برای نسخهٔ جدید از `manage.sh use 0.31.4` استفاده کنید.

اگر هنوز override سازمانی ندارید، نمونهٔ `onprem/compose.override.yaml` نسخهٔ جدید را به `config/compose.override.yaml` کپی کنید، مسیرهای CA/TLS را آماده کنید و issuer و گروه‌ها را با محیط واقعی تطبیق دهید. اگر override سفارشی دارید، تنظیم‌های لازم را ادغام کنید؛ فایل را کورکورانه جایگزین نکنید. در مهاجرت به TLS داخلی، rollback کد به‌تنهایی کانفیگ تغییرکرده را برنمی‌گرداند؛ پشتیبان تنظیمات را هم حفظ کنید.

## آپدیت و شبکهٔ بدون اینترنت

نسخه‌های مستقل Server از کانال `server-vX.Y.Z` منتشر می‌شوند. ابزار جدید `check` و `update vX.Y.Z` همین کانال را بررسی می‌کند. این درخواست‌ها فقط با اجرای فرمان ادمین انجام می‌شوند؛ احراز هویت کاربران به GitHub وابسته نیست.

برای محیط کاملاً ایزوله، IT باید imageها و وابستگی‌های build را با رجیستری/مخزن داخلی تأمین کند و آرشیو نسخه را به‌صورت امن منتقل کند. این بسته نصب offline یک‌کلیکی یا mirror خودکار فراهم نمی‌کند. مدل ابری نیز بدون دسترسی به سرویس مربوط پاسخ نمی‌دهد، حتی اگر AD کاملاً داخلی باشد.
