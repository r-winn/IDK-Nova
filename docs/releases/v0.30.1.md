# Nova 0.30.1 — Local import storage fix

An import failing with `No space left on device (os error 28)` is a disk-space failure, not evidence that the GGUF or Vision projector is incompatible.

- Nova no longer copies the entire GGUF and projector into its own private model directory before passing them to Ollama. The Modelfile points to the original absolute paths; Ollama handles registration into its content-addressed model store. Original files are never modified.
- Before registration, the filesystem containing `OLLAMA_MODELS`, or the normal user `.ollama/models` location, is checked for available space. A conservative new-import estimate includes both files plus a 512 MiB reserve. Insufficient space reports required, available and missing GB before starting large writes.
- Only a small, unique temporary Modelfile is created by Nova. Its own temporary definition is cleaned on success and failure; unrelated imports, original files and previous models are preserved. Old Nova model copies are not deleted automatically.
- Current-layer Ollama progress is explicitly labeled rather than represented as copied GB. Runtime availability no longer asserts that a model can be imported or shown as ready alongside an import error.

## Limits

Ollama still needs storage for a new model. Existing cached layers can require less space than the conservative preflight estimate. If an independently started Ollama service uses a custom directory not reflected in Nova's `OLLAMA_MODELS` environment, the filesystem estimate may differ from the service's actual storage volume. Free space can also change after preflight; Ollama failures remain explicit. Nova does not delete Ollama's partial layers or old user model files without permission.

Native tests check space thresholds and cleanup isolation. Frontend tests/build and locked native tests are run. The full Qwen9B+projector import was not rerun on the user's nearly-full disk; storage must be freed before real inference can be verified.
